# 設計

[English](architecture.md) | [日本語](architecture_ja.md)

## 共通の地図を先に作る

分割器を巨大関数への応急処置にしない。入力全体の原文・構造・依存候補を共通索引に保存し、関数単位、ブロック単位、複数ファイル間の関係を同じIDで参照する。

レイヤーは次の4つ。

1. **言語アダプター**：ソースを読み、位置付きの木と参照候補を返す。
2. **共通索引**：相対パス、原文ハッシュ、安定ID、階層、依存候補の照合を管理する。
3. **入力の組立て**：構造に沿って分割し、祖先の条件・依存先の宣言・例外領域を添える。
4. **検査**：木の整合性、原文一致、全範囲の網羅、予算を検証する。

LLM、埋め込み、ベクトルDB、特定の推論APIに依存しない。共通索引の木と辺は、将来コンパイラ由来のアダプターからも供給できる。

## 決定論の範囲

索引には時刻・絶対パスを入れない。ソースの相対パスと原文ハッシュでsource IDを作り、source ID・種別・範囲・名前でnode IDを作る。ソースが変わればそのソースのID群は変わる。編集をまたぐID追跡は保証しない。

Python ASTは実行環境に依存するためPythonの版を記録する。Java・C#ではTree-sitter本体と文法の版も記録する。原文のバイト列、文字コード、相対パス、実行環境とアダプターの実装版、トークナイザーの語彙・設定、分割設定を固定すれば、出力はバイト単位で再現する。独自アダプターとカウンターも決定論的でなければならない。

ハッシュは材料の同一性を確認するもので、誰が作ったかを証明する署名ではない。

## 分割の規則

1. ノード全体と必要な文脈が入力予算に収まれば、そのまま候補にする。
2. 収まらなければ子ノードと、その前後の原文の隙間に分けて再帰する。
3. 子を持たない範囲は切り刻まない。予算超過なら`oversized`として返す。
4. 隣接する候補を先頭から貪欲にまとめ、まとめ直したpayload全文のサイズで判定する。
5. 余力があれば依存先の宣言やシグネチャを付ける。件数・予算で省略したものはIDと理由を残す。

隙間にはコメント、空白、構造の開始・終了、SQL*Plus区切りなどが含まれる。すべて保存し、全packetの対象範囲を連結するとデコード後の各原文が完全に復元される。補足文脈は対象の網羅性に数えない。

巨大な単一SQL、長い文字列、巨大なヘッダーや認識不能領域は上限を超え得る。その場合にサイズを偽って成功扱いにしない。

## 見出し優先の分割と切れ目の巻き上げ（次の版・実装前）

この節は、次の版で追加する分割方式 `structural-heading-v1` の仕様である。**まだ実装されていない。** 既定の方式は上の規則（`structural-greedy-v1`）のままで、`pack --algorithm structural-heading-v1` を指定したときだけ使う。データ契約は[データ契約](contracts_ja.md)の「次の版で追加する契約」を参照する。

構文だけで分割すると、書き手がコメントで区切った手順のまとまりが、構文の都合で切れたりつながったりする。また、容器のヘッダー（`if` や `for` の行など）や説明コメントが、それが説明するコードと別の packet に分かれることがある。この方式は、書き手の区切り（見出し）を分割の境界として優先し、境界の位置を読みやすい行まで上げる。

1. 範囲が必須文脈込みで予算に収まれば、そのまま候補にする（上の規則1と同じ）。
2. 収まらない関数・手続きの範囲では、その範囲に属する見出しのうち、いま見ている階層の見出しの帯の先頭行を節の境界とする。節を先頭から詰め、次の節を足すと予算を超えるところでだけ切る。小さな節は隣の節と同じ packet になる。
3. 単独でも収まらない節だけ、下の階層の見出しへ降りる。見出しが尽きたら、構文の子へ降りる（上の規則2）。
4. 見出しで選んだ境界も構文で選んだ境界も、切れ目の位置を次の2段で上げる。
   - (1) その位置で本文が始まる容器（制御・分岐・ブロック・ハンドラー）のヘッダー行だけが直上にあるなら、容器の先頭行まで上げる。
   - (2) さらに直上に行コメントの連なりがあれば、その先頭まで上げる（間の空行は飛ばす）。区切り線、変更履歴の行（プロファイルの `markers.change`）、見出しの帯の行は、連なりに含めない。
   これにより、容器のヘッダーが前の packet の末尾に取り残されず、説明コメントは説明する対象のコードと同じ packet に入る。
5. 見出しで選んだ境界は、最後の貪欲な結合で消さない。
6. 切ってよい場所は、リテラル・ブロックコメント・宣言や文・構文ヘッダーの内側を除いた行頭に限る。切れない見出しは文脈に残し、`HEADING_FALLBACK` を注記する。

見出しはプロファイルから検出するので、プロファイルを与えない索引では、この方式は「切れ目の巻き上げ」だけが効く。見出しは書き手の目次であり、その階層を制御フローの証明として扱わない。

## 文脈と依存関係

対象範囲が祖先ノードの一部なら、祖先の原文ヘッダーを添える。IFのELSE側でも外側のIF条件とELSEの位置を失わない。構造から判定した外側の例外領域は参照を残し、予算と依存文脈の件数上限に収まれば原文も追加する。

依存辺は字句から抽出するため、実行時の到達性、呼出先のオーバーロード、変数の最終代入元、例外の伝播を確定しない。`candidate`であっても意味的な解決完了ではない。変数名が一致したことをデータフローの証明にしない。

局所的な「更新なし」「例外なし」をファイル全体の性質へ一般化しない。入力payloadにも解析範囲を明記する。最終的な全体理解は、利用側が複数ブロックの結果と必要な原文を再確認して行う。

## 後から拡張する境界

- コンパイラ／Tree-sitter等によるアダプターの追加
- PL/Scope等の外部根拠に基づく辺の追加
- read/write、reaching definitions、制御フロー、トランザクション情報
- APIでの予算付きの原文追加取得と、目的ごとの依存先優先順位
- 差分索引と編集をまたぐノード対応付け

これらは初版の成果物と区別し、実装前にschema／アダプターの版を更新する。
